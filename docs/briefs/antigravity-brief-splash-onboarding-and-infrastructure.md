## PART 1 — Current Build Task: Splash & Onboarding (React Web)

### Platform note
This is being built **web-first**, using **React + Tailwind + shadcn/ui**, responsive across **mobile and laptop/desktop viewports** — not React Native. A separate React Native build will exist for mobile app-store distribution later, sharing the same visual design but as a fully separate codebase (shadcn does not run in React Native; nothing here should assume otherwise).

### Scope for this task
1. **Splash screen** — auto-playing animation sequence, no user interaction, no shadcn components needed (pure animation).
2. **Onboarding carousel** — 3 slides, swipeable/navigable, using shadcn's `Carousel` (Embla-based) for slide mechanics and `Button` for Skip/Next actions.

### Splash Screen Spec
- Background: `#B69EFF` (confirmed).
- **Static, no animation.** An earlier animated roll-in concept has been dropped — the logo, wordmark, and tagline appear in their resting positions immediately, no motion sequence.
- Logo: the boxed scissor-legged mascot (curvy-cornered tile, black tile background, yellow illustration inside) — pulled from the app's local image assets folder (see "Illustrations" below), not generated in code.
- No shadcn components needed — this is a static layout, responsive to both mobile and desktop viewport sizes without layout shift.

### Onboarding Carousel Spec
- **3 slides.**
- Background: **black** (`#000000` / near-black) — this is part of the confirmed black/purple pivot (see Part 2 for full scope of that pivot).
- Per slide: pill-shaped progress dots (top), "Skip" text link (top, opposite the dots), a **reserved illustration area** (dashed placeholder until real illustrations are supplied — do not generate illustration content), headline (bold, white), one line of supporting body text (muted lavender-gray), and a full-width primary button (`#B69EFF` fill, dark text) — "Next" on slides 1–2, final action on slide 3.
- shadcn components: `Carousel`, `CarouselContent`, `CarouselItem` for the slide mechanics; `Button` for Skip/Next; track current slide via the Carousel API to drive the progress-dot state (dots are custom-styled, not a shadcn primitive).
- Responsive: on desktop/laptop widths, cap the carousel's content column (do not stretch illustration/text full-width edge to edge) and center it — mobile keeps full-width edge-to-edge as designed.

### Illustrations
- **Not to be generated by Antigravity or Claude.** All illustration/image assets live in a local **app image folder** in the codebase — code should reference/import from that folder rather than hardcoding, inlining, or generating illustration content.
- Until an asset exists in that folder for a given placement, use a clearly marked placeholder (dashed border, label) so it's obvious where the real asset slots in.
- **A visual reference image will be supplied for each screen going forward** before it's built — treat that reference as the source of truth for layout/content on that screen, alongside this doc's structural/behavioral notes.

## PART 2 — Full Infrastructure Requirements (Recap — Do Not Drift From This)

### Problem Statement
Tailors often work with clients who live far away and cannot be measured in person. The app lets a client measure themselves remotely with confidence via their phone, and gives the tailor a collaborative dashboard to review, comment on, and manage those measurements through to completion.

### Platform Architecture
| | Web app | Mobile app |
|---|---|---|
| Stack | React + Tailwind + shadcn/ui | React Native |
| Used by | Either tailor or client, via browser | Either tailor or client, via installed app |
| Delivery | Installable PWA (manifest + service worker) — must work well on mobile browsers, not just desktop | App store install |
| Codebase | **Separate project from the mobile app** — not shared UI code | Separate from the web app |

Shared between both: the underlying data model and backend (Supabase) — never UI components, which are platform-specific by necessity.

### Measurement Method (core product logic — do not simplify)
- **No manual (tape) measurement** — measurements come only from the app's own camera-based capture system.
- **Fully on-device processing**: raw photos never leave the client's device; processed in-memory, discarded immediately after. Only derived numeric measurements + calibration metadata sync to the backend — never the photo, never raw pose-landmark coordinates.
- **Calibration**: three combined signals — (1) in-frame/distance gating before capture is allowed, (2) door-frame reference (country sets a regional default, client can override with their door's actual measurement), (3) LiDAR/depth sensing where available, used **together with** the door-frame check, not as a fallback for it. Each submission carries a confidence flag based on how well the signals agreed.
- **Gender-based croquis**: client selects gender at setup, determining which body silhouette renders on their canvas. Female = clean single-line outline, no grid. Male = same style **plus** visible construction grid lines (Prêt-à-Template-style) — a deliberate, confirmed exception to the "no visual noise" rule.
- **Connectivity**: submission requires an active internet connection — no offline queue, no background sync.

### Tailor ↔ Client Connection Model
- One 48-hour expiring link per tailor (not unique per client), renewable by regenerating.
- Client identity resolved by email (new vs. returning).
- Completed measurements land automatically on the tailor's dashboard — no manual linking.

### Data Hierarchy
```
Client (identified by email)
 └─ Project (e.g. "Wedding Suit") — renameable
     └─ Measurement (individual garment)
         ├─ Description (required, per-measurement)
         ├─ Photo-derived measurement values
         ├─ Calibration metadata
         ├─ Confidence flag
         ├─ Canvas / body-diagram visualization
         └─ Comment pins (two-way, pending/resolved status)
```

### Tailor-Side Canvas & Dashboard
- Body-diagram visualization per measurement (not a plain table); comment pins anchored to specific points, two-way, pending/resolved.
- Progress tags: pending review → cutting → fitting → done.
- Queue view, filterable by status; management controls (delete measurements/projects).
- **Black/purple pivot** (confirmed) applies to: onboarding, the dashboard home screen, and the measurement canvas. It does **not** apply to the client's consent/capture/confirmation flow, which stays on the calmer cream/white system — that split is deliberate (trust/precision vs. brand energy) and should not be merged.
- Dashboard home screen: profile chip + tailor's name, a large stat number showing **count of pending reviews** (not a financial figure), one primary action button, then a preview of recent notifications (1–2 items) below.
- Canvas on the dark background: croquis outline in **white** (not the earlier dark-purple-on-cream treatment), pins in the brand purple accent for pending, muted gray-purple for resolved.

### Backend — Supabase
- Chosen for: relational Postgres fit, built-in auth, realtime subscriptions (comment pins, progress tags), row-level security (a tailor only ever sees their own clients' data).
- **Known gap, must be resolved before real use**: the existing build only runs against a **local** Supabase instance — no project has been created on a real hosted Supabase account yet. This is the top-priority infrastructure item once UI work is far enough along.
- Deployment target: **Vercel** (for the web app).

### Build Philosophy (confirmed order — do not revert to backend-first)
1. Build UI for both web and mobile against **mock data**, including edge/empty states (empty queue, zero-comment garment, low-confidence measurement, loading states) — not just the happy path.
2. Validate the full UI/UX before wiring any backend functionality.
3. Only once UI is solid: create a real hosted Supabase project, build the schema, wire auth, replace mock data with live data.
4. Camera/pose-estimation/calibration logic integration follows once the core data flow is proven.

### Explicitly Out of Scope Right Now
- Any backend/Supabase schema work — not until UI is further along.
- Illustration generation — supplied externally.
- The React Native build — web comes first.
